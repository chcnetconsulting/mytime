# Tests

Die Anwendung hat PHPUnit-Tests fuer Controller, Tabellen und Auth-Flows.

**Die Suite muss auf zwei Datenbanken grün sein**: auf SQLite (schnell, ohne
Server, das ist der Standardlauf und was die CI fährt) und auf PostgreSQL (die
Produktionsdatenbank). Der SQLite-Lauf ist dabei mehr als Bequemlichkeit — er
ist der Nachweis, dass keine Abfrage einen Dialekt voraussetzt. Das alte
`ticket REGEXP` ließ die Suite auf SQLite gar nicht erst durchlaufen.

## Standard-Testlauf (SQLite)

```bash
vendor/bin/phpunit --colors=never
```

Alternativ ueber Composer:

```bash
composer test
```

## Lauf gegen PostgreSQL

```bash
createdb mytime_test    # oder: psql -c 'CREATE DATABASE mytime_test'
DATABASE_TEST_URL="postgres://<user>@127.0.0.1:5432/mytime_test" \
  vendor/bin/phpunit --colors=never
```

Die Produktionsdatenbank darf **nie** als Testdatenbank dienen — die Suite
leert Tabellen zwischen den Tests.

Ohne `DATABASE_TEST_URL` und ohne `DATABASE_TEST_HOST` fällt die
Test-Datasource auf SQLite unter `tmp/tests.sqlite` zurück.

Erwarteter Unterschied: **ein** Test wird auf SQLite übersprungen
(`testSecondApprovalWithoutMandantIsRejected`) — er prüft einen Teilindex, den
nur PostgreSQL bekommt.

## Was auf PostgreSQL anders kaputtgeht

Zwei Dinge fallen erfahrungsgemäß erst hier auf, und beide leise:

1. **Sequenzen.** Fixtures schreiben feste IDs; MySQL zieht den Zähler mit,
   PostgreSQL nicht. Der nächste Insert läuft dann in eine
   Eindeutigkeitsverletzung. `tests/Fixture/AppFixture.php` setzt die Sequenz
   deshalb nach jedem Einfügen — alle Fixtures müssen davon erben.
2. **Groß-/Kleinschreibung.** `LIKE` ist in PostgreSQL exakt, in MySQL war es
   das mit `_ci`-Kollation nicht. `BookingsPortabilityTest::testSearchIgnoresCase`
   deckt das ab.

## Migrationen testen

```bash
bin/cake migrations migrate
bin/cake migrations status
```

Danach die Pruefqueries aus [Datenbank und Migrationen](database.md) ausfuehren.
Insbesondere lohnt ein Blick auf `\d bookings` und `\d approvals`: dort muss
`integer … generated by default as identity`, `boolean` und `bytea` stehen.

## Lokaler Smoke-Test

Mit echter lokaler Datenbank, aber ohne OIDC:

```bash
MYTIME_AUTH_DISABLED=true bin/cake server -p 8765
```

Dann im Browser pruefen:

- `http://localhost:8765/bookings`
- `http://localhost:8765/bookings/add`
- `http://localhost:8765/bookings/ticket-lookup?ticket=<ticket>`
- `http://localhost:8765/users`
- `http://localhost:8765/groups`
- `http://localhost:8765/mandanten`

Wieder in normalem Auth-Modus starten:

```bash
bin/cake server -p 8765
```

## Erwartete Testabdeckung

Vorhandene Tests decken ab:

- OIDC Login-Redirect fuer Entra, Keycloak und Google
- OIDC Callback-Validierung
- Bookings CRUD und Zugriffsscope
- Ticket-Lookup
- Mandanten CRUD
- User CRUD inklusive optionaler Admin-Checkbox
- Gruppen CRUD und Admin-Schutz
- Tabellenvalidierung und Beziehungen
- Datenbank-Portabilität (`BookingsPortabilityTest`): Ticket- und PSP-Listen,
  Groß-/Kleinschreibung der Suche, Monatsgrenzen der Exporte
- Binärrundlauf der Approvals (`ApprovalsTableTest`): das gespeicherte PDF muss
  Byte für Byte zurückkommen — der Pfad, der sich zwischen MEDIUMBLOB und
  `bytea` am stärksten unterscheidet

Bei Aenderungen an Auth, Sichtbarkeit oder Migrationen die Suite **auf beiden**
Datenbanken laufen lassen.
