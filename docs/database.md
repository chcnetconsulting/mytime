# Datenbank und Migrationen

MyTime verwendet CakePHP ORM und `cakephp/migrations`. Die Datenbank ist
**PostgreSQL** — in Produktion der gemeinsame Cluster `pgsql92` im
MicroK8s-Namespace `default` (Zalando-Operator, PostgreSQL 17). Das frühere
eigene MySQL ist abgelöst; die Testsuite läuft zusätzlich auf SQLite.

Das Schema entsteht aus **einer** Migration,
`config/Migrations/20260811000000_InitialPostgresSchema.php`. Die fünf
ursprünglichen Migrationen und das einmalige Upgrade-Skript von Mai 2026
liegen unverändert unter `config/Migrations/archive-mysql/` — als Historie,
nicht als Bauplan. Sie werden nicht mehr ausgeführt (Unterverzeichnisse liest
der Migrations-Sucher nicht).

## Tabellen

### `bookings`

Speichert Zeitbuchungen.

Wichtige Felder:

- `id`
- `bookingdate`
- `ticket`
- `bookingpsp`
- `description`
- `minutes`
- `kunde`
- `mandant_id`
- `user_id`
- `group_id`
- `created`
- `modified`

Beziehungen:

- gehoert zu `mandanten`
- gehoert zu `users`
- gehoert zu `groups`

### `mandanten`

Mandanten/Kundenkontexte fuer Buchungen.

Wichtige Felder:

- `id`
- `name`
- `created`
- `modified`

Beziehung:

- hat viele `bookings`

### `users`

Lokale Benutzer, die aus OIDC-Logins entstehen oder durch Admins gepflegt werden.

Wichtige Felder:

- `id`
- `username`
- `email`
- `group_id`
- `is_admin`
- `created`
- `modified`

Beziehungen:

- gehoert zu `groups`
- hat viele `bookings`

### `groups`

Gruppen teilen Buchungen zwischen mehreren Usern.

Wichtige Felder:

- `id`
- `name`
- `created`
- `modified`

Beziehungen:

- hat viele `users`
- hat viele `bookings`

```bash
bin/cake migrations migrate
bin/cake migrations status
```

## Was das PostgreSQL-Schema anders macht als das alte MySQL-Schema

| Punkt | MySQL (alt) | PostgreSQL (jetzt) | Warum |
|---|---|---|---|
| Primärschlüssel | `bigint AUTO_INCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` | `integer` statt `biginteger`, weil SQLite `PRIMARY KEY AUTOINCREMENT` nur für INTEGER vergibt — mit `biginteger` wäre die Testsuite tot. int4 reicht bis 2,1 Mrd., die höchste Buchungs-ID lag beim Umstieg bei 499. `BY DEFAULT` (nicht `ALWAYS`) erlaubt es dem Import, IDs mitzubringen. |
| `users.is_admin` | `tinyint(1)` mit 0/1 | `boolean` | PostgreSQL hat einen echten Wahrheitswert. |
| `approvals.content` | `MEDIUMBLOB` (16 MB) | `bytea` | Ohne Längenangabe: `bytea` trägt bis 1 GB. Die Obergrenze für Uploads ist Anwendungslogik, keine Typgrenze. |
| `bookings.bookingdate` | `DEFAULT (curdate())` | kein Default | Ausdrucks-Defaults bildet der Schema-Layer von CakePHP nicht ab. Die App setzt das Feld immer, die Validierung erzwingt es. |
| `signed` / `unsigned` | teils gesetzt | entfällt | PostgreSQL kennt kein UNSIGNED. |
| Index auf `bookingdate` | fehlte | `idx_bookings_bookingdate` | Jede Abfrage der App sortiert oder filtert danach. |
| Fremdschlüssel auf `approvals` | keine | `user_id`, `mandant_id` | Beim Neuaufbau nachgeholt. |

⚠ **Ein Teilindex, der in MySQL nicht nötig war:** `approvals_period_unique`
greift nicht, wenn `mandant_id` NULL ist — zwei NULL-Werte gelten in SQL nie
als gleich. `ApprovalsTable::findForPeriod()` sucht aber genau danach. Deshalb
legt die Migration zusätzlich `approvals_period_null_mandant` an
(`… WHERE mandant_id IS NULL`), und zwar nur auf PostgreSQL. Der Bezeichner
dafür lautet **`pgsql`**, nicht `postgres` — `PostgresAdapter` überschreibt
`getAdapterType()` genau dafür. Ein Vergleich mit `postgres` scheitert lautlos:
die Migration liefe durch, der Index fehlte.

## Sequenzen: die Falle beim Einspielen fremder Daten

MySQL zieht den `AUTO_INCREMENT`-Zähler mit, wenn Zeilen mit fester ID
eingefügt werden. **PostgreSQL tut das nicht.** Wer Daten mit IDs einspielt und
die Sequenz stehen lässt, bekommt beim ersten neu angelegten Datensatz:

```text
SQLSTATE[23505]: Unique violation … duplicate key value violates
unique constraint "bookings_pkey"
```

Deshalb nach jedem Einspielen:

```sql
SELECT setval(pg_get_serial_sequence('bookings', 'id'),
              COALESCE((SELECT MAX(id) FROM bookings), 0) + 1, false);
```

Erledigt wird das an zwei Stellen automatisch:
`src/Command/ImportMysqlCommand.php` (einmalige Übernahme) und
`tests/Fixture/AppFixture.php` (Testdaten).

## Prüfqueries nach einer Migration

```sql
SELECT 'bookings', count(*) FROM bookings
UNION ALL SELECT 'users', count(*) FROM users
UNION ALL SELECT 'mandanten', count(*) FROM mandanten
UNION ALL SELECT 'groups', count(*) FROM groups;
```

Fehlende Referenzen — alle vier Werte müssen `0` sein:

```sql
SELECT count(*) FROM bookings b LEFT JOIN users u ON u.id = b.user_id WHERE u.id IS NULL;
SELECT count(*) FROM bookings b LEFT JOIN groups g ON g.id = b.group_id WHERE g.id IS NULL;
SELECT count(*) FROM bookings b LEFT JOIN mandanten m ON m.id = b.mandant_id WHERE m.id IS NULL;
SELECT count(*) FROM users u LEFT JOIN groups g ON g.id = u.group_id WHERE g.id IS NULL;
```

Typen und Sequenzen:

```sql
SELECT table_name, column_name, data_type, is_identity, identity_generation
FROM information_schema.columns
WHERE table_schema = 'public'
  AND (column_name = 'id'
       OR (table_name, column_name) IN (('users','is_admin'), ('approvals','content')));

SELECT sequencename, last_value FROM pg_sequences WHERE schemaname = 'public';
```

## PostgreSQL-Hinweise

- `groups` ist auch in PostgreSQL kein unproblematischer Name; die App lässt
  Identifier deshalb weiterhin quoten (`DATABASE_QUOTE_IDENTIFIERS=true`).
- `encoding` muss **`utf8`** heißen, nicht `utf8mb4`: der Treiber setzt daraus
  `SET NAMES` ab, und `utf8mb4` quittiert PostgreSQL mit *invalid value for
  parameter "client_encoding"*. Die MySQL-Unterscheidung entfällt hier ohnehin.
- `LIKE` ist in PostgreSQL **immer** von Groß- und Kleinschreibung abhängig.
  MySQL verglich mit `utf8mb4_*_ci` ohne. Deshalb sucht `BookingsController`
  mit `LOWER()` auf beiden Seiten statt mit `ILIKE` — letzteres kennt SQLite
  nicht.
- MySQL verglich mit PAD SPACE: `'ABC '` und `'ABC'` waren dort derselbe Wert.
  PostgreSQL unterscheidet sie. Der einmalige Import bereinigt `ticket` und
  `bookingpsp` deshalb um Rand-Leerzeichen (drei Werte in den Produktionsdaten).
- Nach Schema-Änderungen immer den Schema-Cache leeren.

## Schema Cache

```bash
bin/cake schema_cache clear
bin/cake cache clear_all
```

Wenn nach einer Migration weiterhin alte Spaltenfehler erscheinen, laeuft oft
noch ein alter Serverprozess oder ein alter Schema-Cache.
